# INN-8: проверка реального провайдера и Telegram

Эта инструкция описывает будущую приёмку. Наличие этого файла не означает,
что проверка уже выполнена. Используйте отдельного тестового бота, отдельные
PostgreSQL/Redis и только открытый тестовый документ.

## Подготовка

1. Выделите тестового Telegram-бота и его токен; не используйте его одновременно
   в других polling/webhook процессах. Проверьте доступность выбранной модели и
   разрешённость передачи данных провайдеру.
2. В отдельном окружении настройте PostgreSQL, Redis и постоянный каталог для
   локального Qdrant. Тестовые данные не должны пересекаться с рабочими проектами
   и базами. Миграции применяются к выделенной базе, не к рабочей.
3. Скопируйте `.env.example` в локальный `.env` и заполните учётные данные
   PostgreSQL/Redis и `BOT_TOKEN`. Для провайдера задайте `RAG_MODE=real`,
   `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `LLM_MAX_OUTPUT_TOKENS` и
   `LLM_MAX_CONCURRENT_GENERATIONS`. Настройте `RAG_QDRANT_PATH` или внешний
   `RAG_QDRANT_URL`. Секреты не отправляются в чат и не коммитятся.
4. Для рассматриваемого Polza API в документации указан base URL
   `https://polza.ai/api/v1`, а ID модели —
   `deepseek/deepseek-v4.1-flash-1017`. Это кандидат, не результат проверки:
   перепроверьте доступность, цену, streaming, `max_tokens` и usage именно для
   выбранного endpoint. `LLM_INCLUDE_USAGE=true` включайте только после проверки
   поддержки `stream_options.include_usage`.
5. При использовании Docker Compose сохраните каталог Qdrant на постоянном
   носителе или используйте отдельный внешний Qdrant: текущий compose-файл не
   объявляет volume для локального каталога Qdrant внутри контейнера бота.
   Иначе после пересоздания контейнера опубликованный PG snapshot может остаться
   без индекса. Избегайте одновременного доступа нескольких процессов к одному
   embedded Qdrant path.

## Сценарий приёмки

1. Примените существующие миграции к тестовой БД, запустите одного экземпляра
   бота в real-режиме и проверьте отсутствие ошибок запуска. Создайте тестовый
   проект и загрузите небольшой открытый TXT/Markdown через REPLACE. Дождитесь
   подтверждения публикации; APPEND пока отключён.
2. В личке задайте вопрос, ответ на который однозначно содержится в документе.
   Зафиксируйте время до первого содержательного draft, наличие реальных delta,
   итоговый ответ и корректные источники. Убедитесь, что после draft появился
   финальный ответ и пользователь не увидел внутренний sentinel или reasoning.
3. Задайте вопрос, которого в документе нет: проверьте no-answer и эскалацию
   админу; инфраструктурный сбой не должен считаться отсутствием знания.
4. На отдельном запросе нажмите stop во время генерации: частичный текст не
   должен стать успешным ответом или попасть в cache. Запросите ещё раз и
   убедитесь, что новый запрос работает. Проверьте output/concurrency limits и
   понятное сообщение при занятости; провайдер не должен вызываться повторно
   из-за повторной отправки Telegram.
5. Сверьте записи попыток в выделенной БД с provider usage: cache hit не создаёт
   новую платную попытку, отсутствующий после stop/ошибки usage — `unknown`,
   а не ноль. Если провайдер не передал usage, проверка reported usage остаётся
   незакрытой. Не помещайте в отчёт ключи, полный prompt и закрытые документы.
6. Сохраните в отчёте commit, версии клиента/модели, название провайдера,
   параметры без секретов, сценарии, наблюдаемые результаты и ограничения.
   Отдельно отметьте реальные действия в Telegram, а не подменяйте их mock-тестами.

## Известные ограничения

- До INN-10 ответы в группах для real-режима выключены. Stop и лимит генераций
  действуют внутри процесса; для нескольких worker нужна общая координация.
- Ledger попыток ещё не обеспечивает полноценные outbox/reconciliation и
  хранение полного корпуса для безопасного APPEND. Сохранение ответа админа
  через `save_knowledge` в real-режиме пока не реализовано.
- Результаты E5/Qdrant local и PostgreSQL-тестов не являются проверкой live LLM
  или Telegram. Критерии INN-8 закрываются только по фактическим результатам.
